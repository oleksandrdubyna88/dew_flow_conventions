## Вывод

У продукта хорошая основа: единый источник правил, проверяемые CLI-инструменты, fixtures и разделение части правил по языкам. Основная проблема — расхождение между сформулированными гарантиями и поведением при неполном результате, ошибке или неверном аргументе.

Найдено **9 проблем**. Самая опасная — удаление каталога вне проверяемого репозитория через `--tag`. Несколько проверок возвращают зелёный exit code, когда требуемая гарантия не установлена. Для самого Claude Code существенно, что весь репозиторий монтируется внутрь автоматически читаемого дерева правил, включая документацию и тестовые примеры.

P1 здесь означает «исправить в ближайшем цикле из-за риска потери данных или недостоверного допуска». P2 — следующий приоритет надёжности и эксплуатации. Это инженерная оценка, не CVSS.

## F1. Непроверенный tag попадает в рекурсивное удаление

**Код:** `tools/http-run.mjs:98`, `:99`, `:154`, `:161`; `tools/lib/paths.mjs:19`.

`within` проверяет suite root и artifacts directory. Затем к artifacts добавляется `tagged-${flags.tag}` без проверки полученного пути. `materialiseTagged` первым действием рекурсивно удаляет destination. Значение tag ещё не проверено на допустимый формат и даже не установлено, что соответствующий запрос существует.

**Воспроизведение:** создан отдельный временный sandbox с fixture-репозиторием и соседним каталогом, содержащим единственный искусственный файл. Конечный путь заранее проверен на принадлежность sandbox. Аргумент tag с `../` вывел destination за fixture-репозиторий. Результат:

```text
outsideRepo=true; sentinelDeleted=true
exit=4; no request in http carries the requested tag
```

Таким образом, даже итоговая «ошибка конфигурации» возникает уже после удаления. httpyac не понадобился. Это риск ошибки аргумента или недоверенного ввода автоматизации, не самостоятельно доступная удалённая атака.

**Исправление:** проверять tag как имя, а не путь; не использовать его в имени каталога без преобразования. Создавать отдельный run directory через безопасный API, проверять конечный путь и принадлежность именно этому запуску перед cleanup. Не удалять произвольный существующий каталог, выбранный флагом. Отдельно проверить symlinks/junctions: нынешний `within` гарантирует только лексическое расположение.

**Приёмка:** разделители, `..`, абсолютные пути и повторный запуск не удаляют ничего вне собственного каталога текущего запуска; отказ происходит до изменения файлов.

## F2. Ошибка тестового процесса теряется при успешных testcase

**Код:** `tools/http-run.mjs:218`, `:219`, `:228`.

После чтения отчёта решение основывается на testcase. Ненулевой `result.code` не участвует в условии успеха; он используется в сообщении только при невалидном отчёте.

**Воспроизведение:** во временном fixture установлен маленький локальный stand-in пакета httpyac. Он написал целый XML с одним успешным testcase и завершился с кодом 9. Настоящий `http-run.mjs` вывел «1 check, 0 failed» и завершился с кодом 0. Никакие HTTP-запросы или установка npm-пакетов не выполнялись.

**Риск:** runner может сообщить успех при ошибке producer после части проверок, teardown или генерации отчёта. Проверка реальной версии httpyac на конкретном аварийном сценарии не выполнялась; подтверждён именно контракт обёртки с дочерним процессом.

**Исправление:** успех требует согласованности process exit, полноты отчёта и результатов проверок. Ненулевой exit без классифицированного объяснения — `inconclusive`/ошибка harness, а не pass. Разделять assertion failure и невозможность завершить suite.

**Приёмка:** целый зелёный XML + exit 9 никогда не дают exit 0; корректный зелёный XML + exit 0 остаются успешными.

## F3. Наличие testcase ошибочно принимается за валидный завершённый отчёт

**Код:** `tools/lib/junit.mjs:55`, `:60`, `:79`, `:96`.

Regex-reader ищет testcase в любом тексте, не проверяет завершённость XML и соответствие счётчиков suite. Элемент `skipped` не учитывается: отсутствие failure/error превращается в pass.

**Воспроизведения:**

1. Обрезанный документ с `tests="2" failures="1"`, одним закрытым успешным testcase и без закрывающих suite-тегов дал `valid=true`, `cases=1`, `outcome=pass`.
2. Целый документ с единственным `<testcase><skipped/></testcase>` через настоящий runner дал exit 0 и «1 check, 0 failed».

Непустой отчёт здесь не доказывает ни завершение suite, ни исполнение проверки. Это отдельная проблема от F2: полностью skipped suite может законно завершить producer с кодом 0.

**Исправление:** валидировать XML проверенным parser с безопасной конфигурацией; учитывать errors/failures/skipped и завершённость документа. Минимум одна реально выполненная проверка и явная политика обязательных запросов; для all-skipped результат `inconclusive`. Выбранное подмножество suite должно отражаться в результате.

**Приёмка:** truncated XML, посторонний текст с testcase, противоречивые counters, all-skipped и смешанный набор имеют отдельные ожидаемые результаты. Старый валидный формат producer остаётся совместимым.

## F4. Завершение родителя отключает уничтожение оставшегося дерева

**Код:** `tools/lib/proc.mjs:11`, `:12`, `:47`, `:53`.

`killTree` сразу выходит, если `child.exitCode !== null`. Но потомок может остаться живым и удерживать stdout/stderr после завершения родителя. `run` ждёт `close`; таймер срабатывает, но дерево не завершается.

**Воспроизведение в WSL / Linux:** короткий parent запустил child с унаследованными pipe и завершился. Child самостоятельно завершался через 1800 мс, чтобы эксперимент не оставлял долговременных процессов. При `timeoutMs=300` получено `timedOut=true`, `code=0`, `elapsedMs=1853`. Возврат произошёл после самостоятельного завершения child, а не на timeout.

На Windows тот же fixture вернулся примерно через 78 мс: этот конкретный механизм удержания pipe там не воспроизвёлся. Windows-реализацию с `taskkill` отдельно следует проверить, но одинаковый дефект на обеих ОС не утверждается.

**Исправление:** учитывать жизненный цикл process group/job, а не только exitCode лидера. Обеспечить ограниченное время teardown и проверяемое уничтожение потомков. На Windows ожидать результат операции завершения дерева; при невозможности завершить процесс возвращать явную ошибку cleanup.

**Приёмка:** родитель жив, родитель уже завершился, потомок держит pipe, отмена в гонке с exit; ни один сценарий не превышает timeout + оговорённый teardown budget.

## F5. Дистрибутив правил содержит документацию и слишком много общего текста

**Код/структура:** `README.md:3`, `:5`; `ROLLOUT.md:1`; `todo/PLAN_prod_checks_and_http_contracts.md:1`; `tools/fixtures/gate/pasted/CLAUDE.md:1`; `common/testing.md:1`; `common/git-workflow.md:1`.

Репозиторий целиком монтируется в `.claude/rules/shared`. На проверенном HEAD tracked Markdown без `paths` составил **35 файлов, 230 472 символа, 3717 строк**. Из них **15 служебных файлов, 38 401 символ** — вне `common/csharp/rust/typescript`, без учёта уже scoped `ROLLOUT.md`. В них входят README, POST_DEPLOY, todo и fixtures. Это не измерение tokenizer: пересчёт в точные токены и latency не выполнялся.

В `common/` отдельно **192 071 символ**: повторяемые истории инцидентов, .NET-специфика в общем testing, длинные процедуры release/PR и абсолютные формулировки. В результате короткая задача получает большой набор инструкций, большая часть которого может к ней не относиться.

По [документации Claude Code](https://code.claude.com/docs/en/memory#organize-rules-with-clauderules) Markdown в дереве rules обнаруживается рекурсивно, а отсутствие `paths` означает безусловную загрузку. Поэтому данная упаковка делает служебные документы кандидатами на загрузку вместе с рабочими правилами. Конкретная установленная версия Claude и фактический список `/context` в пользовательской сессии этим аудитом не проверялись; это вывод из структуры и документированного поведения, а не запись реальной сессии.

Fixtures содержат учебные маркеры gate v2/v5, а планы — ещё не реализованные процедуры. Не установлено, что Claude выполнил неверное действие из-за них; подтверждена причина смешения действующих инструкций с примерами и открытой работой.

**Исправление:** публиковать только предназначенный для загрузки payload правил. Служебные документы и fixtures вынести за его пределы или исключить из обычной загрузки. Сократить всегда нужное ядро, подробные процедуры подключать по задаче, языковые требования ограничить путями. Истории оставить доступными по ссылке. Не сокращать правила вслепую: сначала baseline соблюдения важных ограничений.

**Приёмка:** manifest всех загружаемых файлов; fixtures/todo/отчёты в нём отсутствуют; измеренный context budget по профилям; контрольная сессия подтверждает состав через `/context`.

## F6. Непроверенные pins завершаются сообщением OK

**Код:** `tools/pin-check.mjs:19`, `:24`, `:44`, `:45`, `:57`.

При ошибке `git ls-remote` проверка пишет WARN и пропускает submodule. Если все remote недоступны, результат всё равно «OK — 0 pin(s) at their remote tips», exit 0. CI и offline local не различаются. Ошибка чтения `.gitmodules` также приравнивается к отсутствию submodules. Сетевые git-вызовы не имеют собственного timeout.

**Воспроизведение:** во временном git-репозитории зафиксирован искусственный gitlink, URL указывал на отсутствующий локальный remote. Реальный инструмент напечатал WARN, затем OK и вернул 0. Это не сетевой запрос к рабочим репозиториям.

**Исправление:** считать expected/checked/unreachable; в CI непроверенный pin должен давать `inconclusive` с ненулевым exit, offline tolerance — отдельный явный режим. Отличать повреждённую конфигурацию от отсутствующей. Ограничить время remote-запросов. Отдельно пересмотреть политику «любой pin всегда равен remote HEAD»: для code-submodules это отличается от проверки разрешённой совместимой версии.

**Приёмка:** недоступность одного/всех remote, неверная `.gitmodules`, offline mode, stale pin и корректный pin дают различимые результаты без зависания.

## F7. Coverage может быть зелёным без проверки нужного endpoint

**Код:** `tools/http-coverage.mjs:89`, `:92`, `:129`, `:145`, `:181`, `:244`.

Все `MapGroup` prefixes файла приписываются каждой найденной регистрации. Поэтому запрос одной группы может покрыть endpoint другой группы с таким же tail.

**Воспроизведение:** синтетический C# файл объявлял `/admin/users` и `/public/users`; `.http` содержал только GET `/public/users`. Реальный checker сообщил **2/2 covered, exit 0**. Административного запроса не было. Компиляция C# не требовалась: проверялся именно source scanner.

Дополнительно `--routes` с пустым `[]` и отсутствующим suite дал **0/0 covered, exit 0**. В source-scan режиме уже есть защита от неожиданного нуля, но в предпочтительном режиме route-table её аналога нет.

**Оговорка:** инструмент пишет, что source-scan — bootstrap, и рекомендует runtime routes. Это полезное предупреждение, но не делает цифру 2/2 достоверной. Пустой route table может быть намеренным у продукта без HTTP; такую неприменимость нужно отличать от измеренного покрытия.

**Исправление:** для обязательного gate использовать полные маршруты, полученные от приложения; для неоднозначного scan возвращать unknown, не подбирать любой prefix. Пустую таблицу разрешать явно, с признаком `not applicable`, либо сверять с ожидаемой поверхностью.

**Приёмка:** несколько групп с одинаковым tail, nested groups, маршруты между файлами, пустой и неполный export. Запрос к `/public/users` не засчитывается `/admin/users`.

## F8. Lifecycle-проверка пропускает репозитории только с todo

**Код:** `tools/plan-lifecycle.mjs:269`, `:271`, `:277`.

При отсутствии хотя бы одной из папок `todo` / `research` инструмент выходит до проверки статусов, ссылок и индекса. В самом conventions сейчас есть todo и ещё нет research, поэтому его собственные открытые планы этим инструментом не проверяются.

**Воспроизведение:** временный repo с `todo/PLAN_wrong.md`, статусом IMPLEMENTED и битой ссылкой в README, без research. Результат: «nothing to check», exit 0.

**Исправление:** проверять каждую существующую папку независимо. Отсутствие research допустимо до первой завершённой работы, но не отменяет проверку todo. Обязательные требования к индексу применять только к существующему содержимому.

**Приёмка:** only-todo, only-research, обе папки, ни одной; некорректный существующий план выявляется в каждом применимом случае.

## F9. Захват вывода не имеет границы памяти

**Код:** `tools/lib/proc.mjs:41`, `:43`; `tools/post-deploy-check.mjs:153`; `tools/http-run.mjs:193`.

stdout/stderr накапливаются конкатенацией строк до завершения процесса. Timeout ограничивает время, но не число байт. В `http-run` XML направлен сразу в файл, однако stderr по-прежнему накапливается; post-deploy захватывает оба потока, хотя при успехе показывает только последнюю строку.

**Воспроизведение:** искусственный child вывел 8 MiB; `run` вернул строку со всеми **8 388 608 байтами** на Windows и WSL. Падение из-за OOM намеренно не вызывалось; подтверждены отсутствие cap и полное удержание вывода.

**Исправление:** ограниченный ring buffer для диагностики, потоковая запись полного вывода в артефакт с отдельным лимитом и retention, признаки truncation. Определить поведение при переполнении: остановить процесс или продолжить с ограниченной диагностикой, в зависимости от контракта команды.

**Приёмка:** много stdout, много stderr, большой вывод при timeout; память остаётся в бюджете, усечение видно в результате, журнал не растёт бесконечно.

## Отдельно о настройках и правилах для Claude Code

`settings/settings.json:2` задаёт `acceptEdits`, но также безусловно разрешает `Bash` и `PowerShell`. По [официальной семантике permissions](https://code.claude.com/docs/en/permissions#match-all-uses-of-a-tool) имя `Bash` без шаблона охватывает все Bash-команды. В reference settings нет hooks/deny. Это может быть сознательным выбором владельца для автономной работы, поэтому само по себе не объявляется уязвимостью. Однако запреты в Markdown не следует представлять как техническую защиту исполнения. Границы фактической среды также зависят от managed settings и sandbox, которые здесь не проверялись.

README описывает дополнительный каталог как безусловно не загружающий правила. По [актуальной документации](https://code.claude.com/docs/en/memory#load-from-additional-directories) для дополнительных каталогов существует явная настройка загрузки memory. Следует описывать default и выбранный режим отдельно, с проверкой в используемой версии Claude.

У исходного conventions нет корневого `CLAUDE.md` или собственного рабочего `.claude/rules`, кроме fixtures. Полезно добавить короткую точку входа для Claude, который редактирует сами conventions; README не стоит считать автоматически загруженным контрактом такой сессии.

Приоритет улучшений: безопасные и достоверные инструменты; затем минимальный payload правил с измерением контекста; единый формат результатов проверок; тесты реальных границ; управляемый rollout по версиям. Подробности — в [плане улучшений](PLAN_product_improvements.md).
