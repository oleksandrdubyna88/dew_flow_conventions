# PLAN — надёжность conventions и удобство работы Claude Code

> Status: **plan only, nothing implemented yet, 2026-09-09.** Scope: shared rules, проверяющие CLI, упаковка и rollout; без реализации и изменения pins потребителей.

Основание: [аудит с девятью находками](REVIEW_product_audit_2026-09-09.md). Frontmatter исключает этот backlog из обычной загрузки правил в потребителях, по образцу `ROLLOUT.md`. Статус расположен после frontmatter и заголовка. Документ объединяет приоритеты, а не заменяет существующие планы HTTP/post-deploy и scenario harness.

## 1. Исправить опасные и недостоверные проверки

**Цель:** ошибочный аргумент не удаляет посторонние файлы, а неполная проверка не становится pass.

Основание: `tools/http-run.mjs:99`, `:161`, `:228`; `tools/lib/junit.mjs:55`; `tools/lib/proc.mjs:12`.

- [ ] F1: проверять tag, создавать собственный run directory, удалять только принадлежащие запуску артефакты.
- [ ] F2: учитывать process exit вместе с JUnit verdict.
- [ ] F3: валидировать законченный отчёт, учитывать skipped и обязательные проверки.
- [ ] F4: завершать process group/tree даже после выхода родителя; ограничить teardown.
- [ ] F6: недоступный remote в строгом режиме означает incomplete, не OK.
- [ ] F7: неоднозначный route scan не сообщает точное покрытие; пустая поверхность требует явного объяснения.
- [ ] F8: проверять существующие todo/research независимо.
- [ ] F9: ограничить вывод и память process runner.

**Приёмка:** каждый сценарий аудита воспроизводится до исправления и получает ожидаемый безопасный результат после него; обычные штатные сценарии сохраняются.

## 2. Отделить загружаемые правила от документации

Подключение единого источника к Claude Code и Codex, общий resolver, перенос mount и проверка обоих агентов выделены в [PLAN_shared_rules_claude_codex.md](PLAN_shared_rules_claude_codex.md). Этот раздел остаётся общим backlog требований; отдельный план определяет их реализацию и rollout. Исправления F1–F4/F6–F9 остаются здесь.

**Цель:** Claude получает только действующие и относящиеся к задаче инструкции.

Основание: `README.md:3`, `ROLLOUT.md:1`, `common/testing.md:1`, `common/git-workflow.md:1`.

- [ ] Составить manifest runtime payload: имя правила, область действия, приоритет, размер и причина загрузки.
- [ ] Исключить todo, fixtures, audit reports и инструкции обслуживания из обычного consumer payload.
- [ ] Сохранить короткое безусловное ядро: владение изменениями, реальные результаты проверок, безопасная работа с данными и процессы завершения задачи.
- [ ] Ограничить языковые правила соответствующими файлами; подробные release/review/rollout-процедуры подключать по задаче.
- [ ] Вынести подробные истории инцидентов в справочные документы, сохранив краткое правило и ссылку на основание.
- [ ] Use the shared bootstrap: `CLAUDE.md` contains only `@AGENTS.md`; the resolver selects conditional rules through the single shared entry.
- [ ] Проверять состав через `/context` в поддерживаемой версии Claude Code, включая дополнительные каталоги и worktrees.

**Приёмка:** ни один fixture/план не попадает в стандартный набор; manifest совпадает с реально загруженными файлами; важные инструкции не теряются при сокращении.

## 3. Сделать приоритеты и область правил понятными

**Цель:** уменьшить противоречия и лишние действия без постоянных запросов подтверждения.

Основание: `common/development-workflow.md:5`, `common/reuse-first.md:1`, `common/coai-review-gate.md:4`, `README.md:39`, `settings/settings.json:2`.

- [ ] Различать обязательную техническую границу, рабочую рекомендацию и объясняющий пример.
- [ ] Для правила указывать trigger: docs-only, исправление, новая функция, release, incident, rollout.
- [ ] Явно определить, когда внешний review нужен, какие документы уходят vendor и что делать при неполном составе reviewers.
- [ ] Не запускать одинаковые research/review/checklists по нескольким перекрывающимся правилам.
- [ ] Описать reference settings как профиль автономной работы, включая фактические разрешения shell.
- [ ] Вынести необходимые запреты исполнения в проверяемые controls; дополнительные подтверждения вводить только по выбранной политике владельца.
- [ ] Добавить проверку дрейфа копий settings в потребителях: сейчас byte-identical требуется текстом.

**Приёмка:** типовые задачи имеют один понятный маршрут, обязательные действия не конфликтуют и не дублируются; документированные полномочия совпадают с settings/hooks.

## 4. Единый результат и диагностика всех проверок

**Цель:** человек и автоматизация отличают дефект от неполной проверки, отсутствия применимой поверхности и временного сбоя.

Основание: `tools/http-run.mjs:218`, `tools/pin-check.mjs:57`, `tools/plan-lifecycle.mjs:269`, `tools/post-deploy-check.mjs:199`.

- [ ] Общие состояния: pass / fail / incomplete / not-applicable; явное различие strict и warn-only.
- [ ] Машиночитаемый JSON: tool version, target, commit, selected/executed/skipped, ошибки окружения, elapsed, truncation.
- [ ] Не печатать итоговый OK при нуле проверенных объектов, если объекты ожидались.
- [ ] Для post-deploy отдельно показывать автоматические результаты и неподтверждённые manual items.
- [ ] Валидировать числовые timeout/limits и конфигурацию до побочных эффектов.
- [ ] Сохранять краткий человекочитаемый вывод рядом с машинным результатом.

**Приёмка:** CI может принять решение по результату, не парся случайный текст; отсутствие доказательств не выглядит доказательством успеха.

## 5. Проверять инструменты и поведение Claude на реальных границах

**Цель:** ловить ошибки, которые не замечают существующие 41 тест.

Основание: `tools/selftest.test.mjs:15`, `tools/lib/proc.mjs:30`, `.github/workflows/ci.yml:16`.

- [ ] End-to-end runner tests с локальным producer: корректный XML, exit 9, truncated XML, skipped, отсутствие отчёта, timeout.
- [ ] Процессы: родитель/потомок, удержание pipe, большой вывод, отмена, Windows и Linux.
- [ ] Пути: tag traversal, symlink/junction, вложенные artifacts, параллельные запуски, пробелы и Unicode.
- [ ] Checker fixtures: пустой/недоступный inventory, несколько route groups, только todo, недоступный git remote.
- [ ] Проверка runtime payload и frontmatter на уровне CI.
- [ ] Небольшой набор сценариев поведения Claude: docs-only, чужие незакоммиченные изменения, failed test, недоступный reviewer, root + дополнительный repo, release failure.
- [ ] Отделить детерминированные CI-тесты от model eval: последние имеют выбранную модель, бюджет, данные и явный режим запуска.

**Приёмка:** обычный selftest и интеграционные probes проходят на поддерживаемой матрице; eval измеряет соблюдение выбранных правил, а не просто число вызванных tools.

## 6. Управлять rollout и измерять пользу правил

**Цель:** новая версия conventions улучшает работу потребителей и может быть безопасно откатана.

Основание: `README.md:39`, `:50`, `tools/pin-check.mjs:44`, `POST_DEPLOY.md:3`.

- [ ] Версии policy/tooling, compatibility manifest и краткий changelog поведения.
- [ ] Canary-потребитель перед обновлением всей семьи; продвижение проверенного SHA.
- [ ] Отличать rules pins от code dependency pins: последним нужна проверка совместимости, а не только равенство remote HEAD.
- [ ] Явно показывать принятый SHA, pending updates, недоступные remote и результаты потребительских проверок.
- [ ] Сохранять предыдущую рабочую версию и инструкцию rollback без удаления чужих изменений.
- [ ] Измерять context size, время типовой задачи, стоимость review, число ненужных вопросов и пропущенные/ложные findings.
- [ ] Каждое расширение правила связывать с проверяемым классом ошибок; повторяющиеся объяснения сокращать по результатам измерений.

**Приёмка:** видно, какая проверенная версия действует где; обновление не заставляет автоматически менять несвязанные code pins; canary/rollback проверены.

## Порядок реализации и бюджеты

1. F1–F4 и минимальные проверки их исходных сценариев.
2. F5: чистый payload и baseline фактической загрузки Claude.
3. F6–F9, единые результаты CLI и OS-матрица.
4. Контракты задач/permissions, model eval, rollout по версиям.

Для технического плана предлагаются исходные, ещё не измеренные бюджеты:

- Диагностический tail: не более 1 MiB на поток при обычном запуске; два потока дают около 2 MiB байтового payload, фактическую память JS измерить отдельно.
- Артефакты: 20 MiB на запуск, максимум 100 запусков и 7 дней — до 2 GiB на checkout. Владелец cleanup — runner при старте/завершении; отдельная уборка orphan run directories после crash, с проверкой владельца и активного процесса.
- Контекст: сначала точное измерение supported tokenizer/Claude, затем согласованный cap; стартовая цель компактного общего ядра — до 8k токенов без task-specific процедур. Это цель проекта, не установленный лимит Claude и не уже достигнутый результат.
- Model eval: на первом этапе без постоянной базы, один ограниченный пакет запусков. Ввод истории результатов требует отдельного расчёта объёма, retention, доступа и бюджета model calls.

Бюджеты уточняются в технических планах до первой записи новых постоянных данных. Артефакты не должны содержать секреты; перенос большого вывода на диск не отменяет ограничений объёма и хранения.
